# users-ping-bot (UserPingBot)

Telegram-бот для группового «пинга»: участники группы подписываются, а одна команда упоминает всех подписчиков разом. Права и подписки хранятся в SQLite, токен бота берётся из HashiCorp Vault, бот работает одним контейнером в Docker Compose.

Рассчитан на небольшую нагрузку — единицы одновременных пользователей.

## Роли

- **root** — не больше одного; до первого `set-root` его нет. Назначается только локальной CLI-командой, не через Telegram. Может всё во всех зарегистрированных чатах.
- **admin** — любое число, назначает root. Регистрирует группы и управляет только теми, которые зарегистрировал сам. В чужом чате admin — обычный участник.
- **Хозяин чата** — root или admin, зарегистрировавший этот чат.
- **Подписчик** — участник, подписанный в конкретном чате. Подписка в одном чате ничего не даёт в другом.

Кто не имеет права на команду, не получает от бота ничего — ни ответа, ни ошибки. В незарегистрированной группе бот отвечает только admin и root: на регистрацию и краткой подсказкой по `/upb`, где перечислена регистрация.

## Команды

### В группе

Команды можно адресовать боту явно: `/upb@имя_бота …`.

| Команда | Полная форма | Кто может | Что делает |
| --- | --- | --- | --- |
| `/register` | `/upb chat register`, `/upb register` | любой admin или root — в свободной группе | регистрирует группу |
| `/unregister` | `/upb chat unregister`, `/upb unregister` | хозяин чата | снимает регистрацию и все подписки, бот прощается |
| `/on` | `/upb notify on` | любой участник | подписывает автора |
| `/off` | `/upb notify off` | подписчик, хозяин чата | отписывает автора |
| `/all` | `/upb all`, `/upb notify all` | подписчик, хозяин чата | упоминает всех подписчиков, кроме автора |
| `/list` | `/upb list`, `/upb notify list` | подписчик, хозяин чата | список подписчиков без упоминаний |
| `/help`, `/usage` | `/upb help`, `/upb usage` | подписчик, хозяин чата | справка по доступным командам |
| `/lang en\|ru` | `/upb lang en\|ru` | хозяин чата | язык ответов и меню в этой группе |

Короткая и полная формы равнозначны: права, аргументы и ответы одни и те же. Короткие формы понимают и адресный вариант (`/all@имя_бота`); команда, адресованная другому боту, игнорируется. В личке короткие формы группы не действуют.

Справка показывает команду только короткой формой, обычным текстом — в Telegram по ней можно нажать. В личке команда из двух и более слов (или с пояснением из двух слов) показана так: пояснение строкой, под ним команда отдельным блоком кода.

`/upb` без подкоманды или с опечаткой показывает справку по введённой части — только из тех команд, что доступны автору.

### В личке (только admin и root)

| Команда | admin | root |
| --- | --- | --- |
| `/help`, `/usage`, `/start` | да | да |
| `/lang en\|ru` — язык ответов в личке | да | да |
| `/chat list` | свои чаты | все чаты, с id регистратора |
| `/chat remove <chat_id>` — снять регистрацию одного чата | — | да |
| `/admin create <user_id>`, `/admin remove <user_id>`, `/admin list` | — | да |

`/admin remove` снимает роль и **все чаты, зарегистрированные этим admin**, вместе с их подписками. `/chat remove` снимает только указанный чат и роль регистратора не трогает.

Языки — английский (по умолчанию) и русский. Язык задаётся отдельно для каждой группы и для лички каждого admin и root.

## Развёртывание

**Требования:** Docker с Compose v2, доступный по HTTPS Vault с KV v2.

### 1. Vault

Положите токен бота в KV v2 по пути `<kv_mount>/<secret_path>`, ключ `token`. Создайте AppRole с политикой только на чтение этого пути. Пример политики и требования к SecretID — в `docs/vault-policy.hcl.example`.

Токен бота никогда не пишется на диск: ни в `.env`, ни в БД, ни в логи.

### 2. Конфигурация

```sh
cp .env.example .env    # заполнить VAULT_* и APP_VERSION
```

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `VAULT_ADDR`, `VAULT_ROLE_ID`, `VAULT_SECRET_ID`, `VAULT_SECRET_PATH` | — | обязательны |
| `APP_VERSION` | — | тег образа, который запускает Compose |
| `VAULT_AUTH_MOUNT` / `VAULT_KV_MOUNT` | `approle` / `secret` | точки монтирования в Vault |
| `VAULT_CA_PATH` | системные CA | путь к CA-бандлу внутри контейнера для частного Vault (см. ниже); TLS проверяется всегда |
| `VAULT_TIMEOUT` | `5.0` | таймаут запросов к Vault, секунды |
| `UPB_DB_PATH` | `/data/upb.sqlite3` | путь к БД внутри тома |
| `UPB_LOG_LEVEL` | `INFO` | уровень логов |
| `UPB_PING_COOLDOWN_SECONDS` | `5` | не чаще одного пинга от человека в чате; на root не действует |

Частный Vault: `docker-compose.yml` бандл не монтирует. Смонтируйте его на чтение через `docker-compose.override.yml` и укажите путь в `.env`:

```yaml
services:
  users-ping-bot:
    volumes:
      - ./vault-ca.pem:/etc/upb/vault-ca.pem:ro
```

Файл на хосте должен читаться пользователем контейнера (uid 10001), например `chmod 0644 vault-ca.pem`: с правами `0600` TLS к Vault не поднимется при старте.

```sh
VAULT_CA_PATH=/etc/upb/vault-ca.pem
```

### 3. Сборка и запуск

```sh
make build    # docker build с тегом APP_VERSION из .env
make up       # docker compose up -d
```

`make` без аргументов покажет все цели: тесты, сборку, запуск, логи, назначение root, бэкап и проверку копии. Ниже приведены и сами команды — на случай работы без make.

БД живёт в именованном томе `upb-data` (`/data` в контейнере).

### 4. Первый root

Назначить root, при работающем боте или остановленном:

```sh
make set-root ID=<telegram_user_id>
# то же без make:
docker compose run --rm --entrypoint python users-ping-bot -m app.cli set-root <telegram_user_id>
```

Повторный вызов с тем же id ничего не меняет. Смена root снимает с прежнего роль и все его чаты. Если прежний root когда-либо писал боту, он получит об этом сообщение. Чаты нового root сохраняются.

### 5. Первая группа

Добавьте бота в группу и отправьте от admin или root `/register`.

Настройте, как бот видит сообщения:
- в режиме privacy (по умолчанию у BotFather) надёжно доходят только адресные команды `/upb@имя_бота …`;
- чтобы работали и неадресные `/upb …`, отключите privacy через BotFather (`/setprivacy`) или сделайте бота администратором группы.

Бот выставляет меню команд (кнопка «/» и подсказки при вводе `/`) на языке чата, отдельно по правам:

| Кто | Меню |
| --- | --- |
| все участники зарегистрированной группы | `/all`, `/on`, `/off`, `/list`, `/help`, `/usage` |
| хозяева чата (root и зарегистрировавший admin) | то же и `/unregister`, `/lang` |
| root или admin в незарегистрированной группе (в том числе добавивший бота) | `/register`, `/help` |

Личное меню задаётся отдельно для каждого пользователя в этой группе; `/help` в незарегистрированной группе отвечает только root и admin. Меню обновляется при регистрации и снятии регистрации (любым путём), смене языка, снятии роли admin, смене root, переезде группы в супергруппу и добавлении бота; при этом проверяются все текущие root и admin. Если root сменили через CLI при работающем боте, меню активных групп обновляется, когда бот доставит бывшему root уведомление о снятии роли (или откажется от доставки). При запуске бот сверяет меню всех известных чатов. Ошибки Telegram при этом только пишутся в лог (например, если человека уже нет в группе). Меню бывшего root, которому уведомление не ставилось в очередь (у него не было личного диалога с ботом), не обновляется: бот о нём не знает. Короткие команды без `@имя_бота` в группе с несколькими ботами при включённом privacy могут не дойти до бота — используйте `/all@имя_бота`.

## Эксплуатация

**Обновление.** Соберите образ с новым тегом, поменяйте `APP_VERSION` в `.env` и выполните `docker compose up -d`. Данные остаются в томе. Если контейнер от старого compose-файла (например, под прежним именем сервиса) ещё существует, `docker compose up -d --remove-orphans` заменит его; иначе два процесса будут опрашивать Telegram одним токеном.

**Откат на версию без меню команд (до v1.1).** Меню команд в группах останется: старая версия его не ставит и не убирает, а выбранные пункты (`/all`, `/on` и т. д.) молча игнорирует. Чтобы меню исчезло, перед откатом снимите регистрацию групп (`/unregister` в группе или `/chat remove` в личке) на новой версии (подписки этих групп тоже снимутся); иначе оставьте меню как есть. Личное меню (`/register`, `/help`) у root и зарегистрировавшего admin после снятия регистрации остаётся: старая версия его игнорирует и не убирает. Оно безвредно; при возврате на v1.1 первый запуск заменит его актуальным.

> Не выполняйте `docker compose down -v`: флаг `-v` удаляет том с БД.

**Бэкап** — согласованный снимок через SQLite backup API, безопасен при работающем боте. Все шаги идут через том данных, поэтому права на каталоги хоста не важны. Файлы передаются потоком через stdin/stdout одноразового контейнера от пользователя сервиса (uid 10001), а не `docker compose cp`: так файл в томе принадлежит нужному пользователю, а копия на хосте — оператору (по его umask). Флаг `-T` (без TTY) обязателен: иначе поток портится. `make backup`:
- создаёт `backups/` и выставляет ему режим 0750 (это же исправляет каталог 0777 от старого `Makefile`);
- пишет копию внутрь тома (`/data/backups/`) и проверяет её там;
- передаёт проверенную копию потоком в `backups/<имя>.part` на хосте и переименовывает в `<имя>` только после успеха (оборванная передача не выглядит готовым бэкапом);
- только после этого удаляет копию внутри тома (полный том ломает запись в БД). Если копирование не удалось, копия в томе остаётся (повторный бэкап с тем же именем перезапишет её и без `FORCE=1`: `FORCE=1` защищает только файл на хосте).

Имя файла — `upb-<дата>_<ччммсс>.sqlite3`. `BACKUP_FILE=<имя>` задаёт только имя файла (каталог из значения отбрасывается: копия всегда в `backups/`). Если `backups/<имя>` уже есть, `make backup` отказывает с кодом 2 и ничего не трогает; перезаписать можно только явно: `FORCE=1 make backup BACKUP_FILE=<имя>`. Вручную (проверку существования файла на хосте делайте сами):

```sh
mkdir -p backups && chmod 0750 backups
f=upb-$(date +%F_%H%M%S).sqlite3
test ! -e backups/$f &&
  docker compose run --rm --entrypoint python users-ping-bot -m app.cli backup --force /data/backups/$f &&
  docker compose run --rm --entrypoint python users-ping-bot -m app.cli verify /data/backups/$f &&
  docker compose run --rm -T --entrypoint sh users-ping-bot -c "cat /data/backups/$f" > backups/$f.part &&
  mv backups/$f.part backups/$f &&
  docker compose run --rm --entrypoint sh users-ping-bot -c "rm -f /data/backups/$f"
```

После неудачной проверки или передачи копия в томе остаётся. После неудачной передачи `backups/<имя>.part` на хосте нужно удалить вручную (после неудачной проверки его нет: передача идёт после проверки).

Существующий контейнер сервиса не нужен.

`make verify FILE=backups/<файл>` сначала передаёт файл с хоста в том (`/data/backups/`) потоком, затем проверяет его там и в любом случае пытается удалить копию из тома (данные остаются на хосте). После неудачной проверки он сообщает, что копия удалена, а если удалить её не удалось, завершается с ненулевым кодом даже при успешной проверке. Вручную (шаги связаны через `&&`; удаление копии выполните и после сбоя проверки):

```sh
docker compose run --rm --entrypoint sh users-ping-bot -c 'mkdir -p /data/backups' &&
  docker compose run --rm -T --entrypoint sh users-ping-bot -c 'cat > /data/backups/<файл>' < backups/<файл> &&
  docker compose run --rm --entrypoint python users-ping-bot -m app.cli verify /data/backups/<файл>
docker compose run --rm --entrypoint sh users-ping-bot -c 'rm -f /data/backups/<файл>'
```

Копия — один самодостаточный файл. На существующий файл бэкап пишет только с `--force`, а на рабочую базу и её `-wal`/`-shm`/`-journal` не пишет никогда.

**Восстановление** — при остановленном боте, после `make verify` нужной копии. Шаги цепочкой `&&`, начиная с `docker compose stop`: после первого сбоя (в том числе остановки) следующие не выполняются. Копия передаётся потоком в том и проверяется там (`app.cli verify`); пока это не удалось, рабочая БД не затрагивается. Затем копия копируется во временный файл рядом с БД, убираются старые `-wal`/`-shm` (иначе SQLite применит их к восстановленному файлу), временный файл переименовывается поверх БД и удаляется копия в `/data/backups/`. Гарантия: сбой передачи, проверки или копирования оставляет рабочую БД нетронутой. Сбой после удаления `-wal`/`-shm` (на практике только `mv`) уже не откатывается: остаётся прежний файл БД без своих `-wal`/`-shm`, а временный файл — рядом; повторите восстановление. Неполный `/data/upb.sqlite3.restore` после сбоя `cp` бот не читает, следующее восстановление его перезапишет. Копия в `/data/backups/` при любом сбое остаётся в томе: удалите её вручную. При сбое бот остаётся остановленным — запустите его (`docker compose start`), когда разберётесь с причиной.

```sh
docker compose stop &&
  docker compose run --rm --entrypoint sh users-ping-bot -c 'mkdir -p /data/backups' &&
  docker compose run --rm -T --entrypoint sh users-ping-bot -c 'cat > /data/backups/<файл>' < backups/<файл> &&
  docker compose run --rm --entrypoint python users-ping-bot -m app.cli verify /data/backups/<файл> &&
  docker compose run --rm --entrypoint sh users-ping-bot -c \
    'cp /data/backups/<файл> /data/upb.sqlite3.restore &&
     rm -f /data/upb.sqlite3-wal /data/upb.sqlite3-shm &&
     mv /data/upb.sqlite3.restore /data/upb.sqlite3 &&
     rm -f /data/backups/<файл>' &&
  docker compose start
```

**Вывод CLI.** Вывод `set-root` и `backup` начинается со строки `db=<путь>`; у `verify` в ней путь проверяемого файла. Ошибки разбора аргументов `db=` не печатают. Если файла БД нет, `set-root` предупреждает, что создаёт новый, — так видна опечатка в `UPB_DB_PATH`; `backup` без БД завершается ошибкой.

**Запуск бота:**
- проверяет, доступны ли все зарегистрированные группы; из недоступных (бота удалили, чат исчез) снимает регистрацию;
- присылает root отчёт со списком чатов — если root писал боту: Telegram не даёт боту писать первым.

**Аварийный выход** — после паузы 60 секунд, чтобы перезапуски не частили логинами в Vault. Пауза идёт после закрытия БД и сессии Telegram; `docker compose stop` её прерывает.
- код 3 — токен бота отклонён;
- код 1 — любая другая фатальная ошибка, например: 10 подряд ошибок получения обновлений, ошибка Vault на старте, сбой `getMe`, схема БД новее кода, ошибка БД при сверке чатов или стартовой очистке.

Ошибка конфигурации завершает процесс сразу с кодом 1, без паузы.

**Логи.** Наш код пишет только коды событий и id, без секретов и текстов сообщений. Логгеры `aiohttp`, `aiogram`, `aiosqlite`, `urllib3` и `requests` держатся на уровне WARNING даже при `UPB_LOG_LEVEL=DEBUG`.

**Ресурсы** (`docker-compose.yml`):
- 0.25 CPU, 192 MiB RAM без swap, 64 процесса, core dump выключен;
- read-only rootfs, `/tmp` в tmpfs 16 MiB;
- все capabilities сброшены, запуск от непривилегированного UID 10001.

## Поведение, которое стоит знать

- **Пинг.**
  - Получатели фиксируются в момент команды: права и подписки проверяются один раз, дальше реакция считается одной операцией.
  - Автор команды в пинг не входит; если упоминать некого — ответ `pong`.
  - Упоминания всегда по `tg://user?id`, не по username, по 50 на сообщение.
  - Ответ на `429` бот повторяет до трёх раз на сообщение. Любая другая ошибка останавливает рассылку. Если команду удалили до ответа, пинг отменяется.
  - Доставка push-уведомлений не гарантируется: она зависит от настроек получателя.
- **Обработка по очереди.** Пока идёт пинг, следующие команды ждут своей очереди. При таком масштабе это доли секунды, при ответе `429` — дольше.
- **Уход участника** снимает его подписку в этом чате. Бот видит уход по служебному сообщению. Полные события участников Telegram присылает, только если бот — администратор группы. Возвращение участника подписку не восстанавливает.
- **Бота удалили из группы** — регистрация и подписки снимаются. После повторного добавления бот молчит до новой регистрации.
- **Группа стала супергруппой** (Telegram меняет ей id) — регистрация и подписки переносятся автоматически. Если к этому моменту бота в группе уже не было, новую супергруппу нужно зарегистрировать заново.
- **Прощания и уведомление прежнему root** идут через очередь в БД. Поэтому они доходят и после перезапуска — не больше трёх попыток. Возможен редкий дубль. Обработанные события (отправлены, не доставлены, отменены) старше 30 дней удаляются раз в час вместе с записями об обработанных обновлениях; ожидающие не удаляются никогда.

## Разработка

```sh
make test    # создаёт .venv при первом запуске; ARGS="-k ..." передаёт аргументы pytest
```

Тесты работают на временной SQLite и фейковых транспортах. Они не читают `.env` и не ходят в сеть.

Код — в `src/app/`:

| Модуль | Отвечает за |
| --- | --- |
| `access.py` | матрица прав |
| `commands.py` | разбор команд |
| `rendering.py` | тексты на en/ru и экранирование |
| `services.py` | всё изменение состояния |

## Не проверено на живых сервисах

Всё ниже покрыто тестами на фейках, но на реальном Telegram и Vault не проверялось:
- как Telegram разбирает отправляемый HTML;
- `message_thread_id` вне тем форума;
- лимит упоминаний в сообщении и push при упоминании;
- доставка команд в режиме privacy;
- `chat_member` без прав администратора у бота;
- ответы `getChatMember` для удалённых и мигрировавших чатов;
- эффективная политика Vault;
- поведение контейнера под реальной нагрузкой.
